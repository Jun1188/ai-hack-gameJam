# 한글 잡담과 로컬 모델

`CafeSession`이 선택한 대기 손님의 첫 잡담을 표시한다. 플레이어는 커서 모드에서 왼쪽 한글 입력창에 최대 300자를 넣고 Enter/보내기로 답한다. 조합 중 Enter는 전송하지 않으며 입력 중 이동·시점 전환 키를 막는다. 전송 중에도 큐는 계속 진행한다. 손님 전환·서빙·시간 초과·중단·초기화 시 이전 요청을 폐기한다. 대화 오류는 주문과 서빙을 중단시키지 않는다.

입력창은 새 Input System과 호환되는 UI Toolkit TextField이고 나머지 HUD는 기존 IMGUI다. `CafeChatPanelSettings`·`CafeChatTheme`와 기존 NotoSansKR 폰트에서 만든 `CafeChatKoreanFont`를 Resources에서 읽는다. Input Handling 설정 변경이나 Editor 재시작을 요구하지 않는다. 입력창은 HUD와 동일한 화면 비율에 배치하며 조합 확정 프레임의 Enter는 전송에 쓰지 않는다. `tools/cafe-chat-input-check.cs`로 패널·테마·한글 글리프·문자 보존을 검사한다. 실제 OS 자모 조합은 사용자 Play 검증 항목이다.

## 검색 및 응답 정책

`Resources/CafeKnowledge/conversation.json`은 기존 96개 대기 잡담 바인딩, 첫 잡담에 연결한 32개 후속 답변, 16개 인사를 담는다. 기존 어휘와 시간·상태 조건, 손님 ID, 첫 잡담 어휘 ID, 예상 질문, 주제 단어, 말투를 연결한다. 12개 동의어 묶음과 16개 말투별 종료 문장도 포함한다. 후속 답변과 동의어는 원본 엑셀 내용과 구분한 수작업 파생 데이터다. 생성된 사용자 대화를 자동으로 DB에 저장하지 않는다.

- Unicode 정규화 후 한글을 포함한 2글자 묶음 Dice 유사도 80%와 질문 단어 포함률 20%를 계산한다. 동의어 확장을 함께 비교한다. 이는 임베딩에 기반한 의미 이해가 아닌 로컬 어휘 휴리스틱이다.
- 검색은 같은 손님과 현재 시간·상태 조건으로 좁힌다. 후보 순위는 질문/어휘 유사도 65%와 직전 자발적 잡담 유사도 35%다. 상위 세 문장의 말투와 내용을 모델 참고 자료로 전달한다. 자동 잡담의 사용 어휘 기록은 소비하지 않는다.
- 답변 생성은 설정된 API → 로컬 LLM → 자동 답변 순서다. DB 직접 응답과 문맥 캐시는 모델 호출보다 앞서 반환하지 않는다. API 설정·키 누락, HTTP 오류·시간 초과, 빈 응답·잘린 응답·대화 JSON 계약 위반 시 다음 단계로 넘어간다. 로컬 LLM은 기존 페이로드를 필요할 때 부팅하며 별도 API 키와 로컬 인증 토큰을 분리한다.
- 자동 답변은 같은 손님·현재 시간·상태 조건으로 `conversation.json`을 검색한다. 최고 유사도 후보의 점수가 `CafeSession.automaticReplyThreshold` 이상이면 그 매크로를 사용한다. 기본 기준은 0.60이며 Inspector에서 조정한다. 미만이거나 후보가 없으면 `replyVocabulary`의 손님별 맞장구·되묻기·주제 질문 어휘를 조합한다. 확실하지 않은 사실을 만들어 내지 않고 설명을 요청하며, 자발적 잡담의 사용 기록을 소비하지 않는다.
- API와 로컬 모델 모두 페르소나·실제 주문/제공·최근 대화를 참고해 자유롭게 새 대사를 생성한다. DB 예시와의 문장 일치를 요구하지 않는다. 새 화제·낮은 어휘 유사도·모르는 질문은 대화 종료 조건이 아니다. 플레이어의 명확한 작별 입력과 모델의 `endConversation=true`가 함께 있을 때만 생성 대화 UI를 닫으며 생성된 작별 대사를 유지한다. 자동 답변도 명확한 작별 입력에만 종료한다. 기존 speech-only 응답은 대화를 유지한다. `다시 이야기하기`로 재개한다.
- 모델 단계에서 JSON `speech`와 한국어·길이·미해결 슬롯·시스템 오류 문구를 검사하고 기존 메뉴명 마스킹을 적용한다. 빈 응답/잘린 응답/HTTP 오류/진단 형태의 대사에는 해당 단계의 결과를 버리고 다음 순위로 넘어간다. 오류 원문을 손님 대사나 재시도 요청으로 표시하지 않는다. 대화가 주문·서빙·별점 상태를 수정하지 않는다.
- 최근 기록 8개를 방문별 문맥으로 전달한다. 라이브 경로는 답변 완성본 캐시를 사용하지 않는다. 기존 `Remember/TryCached`는 호환·검사용으로 남아 있다. 실제 재사용 대상은 최대 32개 페르소나 래퍼와 손님별 검색 인덱스, 로컬 서버의 공통 프롬프트 앞부분 KV 캐시다. 래퍼 캐시에는 원본 인물 자료만 들어가며 플레이어 대화는 넣지 않는다. 초기화하면 메모리 캐시와 대화 종료 상태도 지운다.

## 모델 및 빌드 검증 방법

### API 연결 옵션

MainMenu에서도 `MainMenuController` 컴포넌트 하단의 **API 키 직접 입력** 토글을 사용할 수 있다. CafeGame의 `LocalCafeModel` Inspector와 같은 키/토글을 공유하므로, MainMenu에서 입력한 키는 게임 시작 후 API 연결에 적용된다. MainMenu에 추론 컴포넌트를 추가하거나 로컬 모델을 미리 부팅하지 않는다.

MainMenu의 `MainMenuController`와 CafeGame의 `LocalCafeModel` Inspector에서 **API 키 직접 입력** 토글·마스킹 입력·키 삭제를 함께 제공한다. 사용자 요청으로 토글과 입력 키를 로컬 `Assets/CafeSim/Resources/CafeApiRuntimeSettings.json`에 저장하며, 이 PC에서 만드는 빌드에도 Resources로 포함한다. 해당 파일과 `.meta`는 Git에서 제외한다. 다른 PC에서 빌드할 때는 그 PC에서 키를 다시 입력해야 한다. Play 중 변경 후 **API 키 적용 · 응답 연결 재시작**을 누르면 진행 중 요청을 취소하고 재연결한다. 키 선택은 현재 실행의 인게임 키 → 직접 입력 토글이 켜진 로컬/빌드 설정 → 환경변수/기존 Gemini 로컬 파일 순서다. 토글이 켜진 상태에서 빈 키를 넣으면 기존 환경변수로 되돌아가지 않는다. `LocalModel` 제공자는 API 키를 사용하지 않는다.

2026-11-06 현재 소스 재검사와 남은 사용자 Play 항목은 [cafe-next-steps.md](cafe-next-steps.md)에 기록했다. 앞선 Play/빌드 시간 기록과 최신 검증 범위를 구분한다.

`LocalCafeModel` 새 컴포넌트의 `backend`는 기본 `Gemini`다. 기존 씬의 직렬화된 제공자 선택은 유지한다. `CompatibleApi`로 바꾸면 실시간 생성에만 외부 OpenAI 호환 Chat Completions API를 사용한다. `apiEndpoint`에는 전체 `/v1/chat/completions` 주소, `apiModel`에는 제공자 모델 ID, `apiKeyEnvironmentVariable`에는 키 **값이 아닌 환경변수 이름**을 넣는다. 기본 이름은 `CAFE_CHAT_API_KEY`다. 키가 없는 자체 서버라면 Inspector에서 환경변수 이름을 비운다. 기존 씬에는 주소와 모델명만 직렬화한다. 환경변수 방식은 키를 별도로 저장하지 않으며, 직접 입력을 켠 경우에는 위 로컬/빌드 설정을 사용한다.

빌드에서도 실행 인수로 선택할 수 있다. 환경변수는 실행 전에 사용자가 설정한다. Unity Editor 역시 해당 환경변수를 상속받은 상태로 실행해야 한다.

```powershell
.\CafeChat.exe --cafe-chat-provider api --cafe-chat-endpoint https://provider.example/v1/chat/completions --cafe-chat-model MODEL_ID
```

`--cafe-chat-key-env 다른_환경변수명`으로 키의 환경변수 이름을 변경하고, `--cafe-chat-provider local`로 로컬 모델을 선택한다. API를 선택하면 실패 시 같은 요청을 로컬 LLM으로 넘긴다. `local` 명시 선택은 API 설정이 없는 오프라인 모드이며 로컬 LLM → 자동 답변 순서로 동작한다. API 준비 상태는 설정 검사 결과이며 인증·연결 성공은 첫 전송에서 확인된다. HTTPS를 요구하며 인증정보가 포함된 URL·쿼리·fragment는 거부한다. HTTP는 loopback 개발 서버만 허용한다. 호환 API가 `messages`, `max_tokens`, `temperature`, `response_format: json_object`와 `choices[].message.content` 형식을 지원해야 한다. 다른 네이티브 API 규격은 별도 어댑터가 필요하다.

실제 외부 API 호출과 키 생성은 수행하지 않는다. `tools/cafe-api-mock.py`는 루프백에서 모델명·Authorization·한글·문맥 전달·JSON 계약을 검사하며 실제 인증정보를 사용하거나 로그에 남기지 않는다.

`LocalCafeModel.PayloadPath`는 Editor에서는 `LocalInference`, Windows Player에서는 실행 파일의 `_Data/StreamingAssets/CafeLocal`이다. 씬 시작 시 자체 프로세스를 부팅하고 준비 상태를 표시한다. 준비 중에도 입력을 접수하고 준비 완료 후 순차 생성한다. 로컬 모델도 사용할 수 없으면 자동 답변으로 이어간다. `모델 재시작`은 큐를 초기화하지 않는다. 기존 검증된 페이로드를 재사용하며 패키지나 모델을 새로 설치하지 않는다.

`tools/cafe-conversation-check.cs`는 16명별 첫 잡담 매핑, 맞장구·후속 질문 허용, 무관한 질문 거절, 검색 부작용, 응답 검증 및 캐시 분리를 검사한다. 기존 큐 회귀 검사는 `tools/cafe-queue-check.cs`다.

Development 빌드에서 `CafeChat.exe --cafe-chat-smoke <절대 경로.json>`을 명시할 때만 통합 검증이 실행된다. 일반 실행이나 씬에는 자동 검사 오브젝트를 붙이지 않는다. 빌드에 포함된 모델 부팅, DB 답변, 실시간 생성 2회, 문맥 캐시 분리, 취소, 손님 전환, 화제 이탈 종료와 서빙을 검사하고 JSON과 화면 캡처를 남긴 뒤 종료한다. 합성 검사 문장 외의 사용자 대화는 저장하지 않는다. 이 검사는 API를 통한 한글 전송을 확인하며 OS IME의 실제 자모 조합 입력을 대신하지 않는다.

이전 버전의 Windows 빌드 `Builds/CafeChat-20261105-Api/CafeChat.exe`에서 로컬 모델 부팅, DB 답변, 생성·문맥 응답, 취소·손님 분리·화제 이탈 종료·서빙 검사가 모두 통과했다. CPU 생성은 27.92초와 27.06초였으며 DB 답변은 같은 프레임에 처리됐다. 같은 최종 빌드의 API 옵션도 루프백 모의 서버에서 통과했고 모델명·Authorization·한글·최근 답변 문맥 전달을 확인했다. 모의 서버 지연은 실제 외부 API 속도의 근거가 아니다.

빌드는 오류 0건으로 성공했다. 설치된 추론 패키지 compute shader의 variant 경고 496건은 남아 있다. OS IME 자모 조합 입력, 외부 API 실호출, 다른 PC 실행은 미검증이다. 실제 화면에서는 로컬 모델 준비와 대화 종료·재개 UI를 관찰했지만 사용자 입력이 감지되어 창의 키 입력 자동화는 중단했다. [현재 빌드·실행 근거](cafe-chat-verification.json)에 검사 결과를 기록했다. 빌드 자동 변경 설정과 임시 씬은 정리하고 기존 패키지는 유지했다.

## 새로운 메뉴 단답과 현재 검증

`Resources/CafeKnowledge/NewMenuRequests.json`은 표시명 **새로운 메뉴**인 별도 테이블이다. 기존 메뉴 밖 요청 4종 × 손님 16명의 64개 단답을 보관한다. 요청 ID·손님 ID로 원하는 메뉴명과 기존 주문 어미를 결합한 답변을 찾는다. 예: “카페모카 부탁하겠네.” 메뉴 밖 주문이 active 상태일 때 입력창에서 “무슨 메뉴를 원하세요?”, “그 음료는 없어요”, “대신 라떼는 어떠세요?”라고 응대하면 이 테이블의 API와 로컬 LLM이 모두 실패한 자동 답변 단계에서 원하는 메뉴 단답을 반환한다. 이 단답에는 메뉴명을 마스킹하지 않는다. 주문·별점 상태를 바꾸거나 대체 메뉴에 동의했다고 해석하지 않는다. 잡담이 종료된 뒤에도 메뉴 문의는 가능하다.

이번 버전은 빌드/Play 없이 Editor 컴파일과 접수·단답·자연스러운 후속 질문·큐·후기·데이터 검사를 통과했다. 의미 판단을 위한 새 모델 응답 계약은 코드/파서 호환성만 검사했고 실제 모델의 새 응답 품질은 미검증이다. 이전 빌드의 실행 기록은 현재 버전 성공 근거가 아니다. 사용자가 삭제를 요청한 두 CafeChat 빌드 폴더는 삭제했으며 기존 Builds/Windows와 원본 LocalInference는 보존했다.

## 입력창 표시와 다음 손님 복구

첫 손님을 일찍 서빙하면 다음 정기 입장까지 빈 화면이 생기던 문제를 수정했다. 마지막 손님의 후기 읽기 시간이 끝났고 Active/Inactive가 모두 비었을 때만 FillVacancy로 다음 손님을 입장·접수한다. 정기 입장 시각도 재설정해 중복 입장을 막는다. 다른 대기자가 있으면 기존 FIFO를 유지한다. tools/cafe-continuity-check.cs는 세션의 후기 보존 → 두 번째 손님 선택 → CanChat까지 검사하며 시간 초과와 중복 방지도 포함한다.

입력 불가처럼 보이던 원인은 두 가지가 겹쳤다. 작은 Game View에서 기본 테마의 입력칸 상하 여백 각 10px 때문에 내부 TextElement 높이가 0이 됐고, IMGUI 배경이 UI Toolkit 입력창 위에 그려져 문자와 커서를 덮었다. 입력 필드 내부 여백·최소 높이를 화면 배율과 함께 설정하고 IMGUI 배경에는 입력칸 영역을 비워 둔다. 테마의 커서·선택 색도 명시한다. 입력 활성 여부는 Repaint 대신 Update에서 갱신한다.

사용자가 이번 입력 문제에 한해 허용한 Editor Play에서 마우스 클릭 후 커서 표시, hello 한글 및 안녕하세요의 실제 입력·화면 표시를 확인했다. 수정 전 내부 문자 버퍼는 8자였지만 글자 영역 높이는 0이었고, 수정 후 같은 작은 화면에서 높이 15px를 확보했다. OS 한글 자모 조합 자체와 Enter 전송은 이번 재현 검사로 확정하지 않았다. Play는 종료했고 빌드는 생성하지 않았다.

## 2026-11-06 답변 우선순위 변경

일반 대화·새로운 메뉴 문의·화제 이탈 모두 API → 로컬 LLM → 자동 답변 경로로 처리한다. 생성 성공 시 실제 사용한 소스를 기록하며, 자동 답변의 내부 점수·ID는 UI에 표시하지 않는다. 요청 중단·손님 전환·서빙·초기화는 전체 순차 요청을 취소한다. 기존 `CafeChatSmoke`의 DB 검사는 자동 답변 함수를 직접 검사하도록 바꾸었으며 일반 실행에는 검사를 연결하지 않는다.

Unity의 Resources/JSON/Mathf를 대체한 검사이므로 Editor 실행 근거는 아니다. 실제 `LocalCafeModel` 소스에 모의 통신을 연결한 검사에서 API 성공 시 로컬 미호출, HTTP 오류와 잘못된 JSON의 로컬 전환, 두 모델 실패 콜백, 인증 토큰 분리를 통과했다. 실제 네트워크·추론 프로세스·취소 UX는 이 검사로 입증하지 않는다. 패키지 manifest/lock 해시는 변경 전과 동일하다.

## 어휘 조합의 후보 생성·필터·순위 선택

`CafeReplyComposer`가 낮은 유사도 자동 응답의 최종 문장을 선택한다. 입력의 대화 행위를 인사·맞장구·질문·불명확 입력으로 나누고, 손님별 작성된 어휘와 현재 입력에서 근거가 확인되는 DB 주제로 후보를 생성한다. 미완성 슬롯, 중복 문장, 비정상 구두점, 길이·표현 제한을 위반한 후보는 제거한다. 관련성·대화 행위 일치도·간결성으로 점수를 매기고 최근 손님 답변 3개의 동일·유사 표현에 반복 감점을 적용한다. 근거가 부족하면 일반 확인 질문을 선택한다. 인사·맞장구에 불필요한 되묻기를 붙이지 않는다.

이는 문장 후보를 생성한 다음 필터와 순위 선택을 거치는 구조를 적용한 프로젝트 전용 규칙이다. 참고: [Generate, Filter, and Rank](https://arxiv.org/abs/1904.03279), [Joint Generator-Ranker Learning](https://aclanthology.org/2023.findings-acl.486/). 해당 논문의 학습 모델·평가 결과를 이 구현에 적용한 것으로 해석하지 않는다. 현재 필터는 한국어 문법·의미 함의를 학습한 판별기가 아니며, 0.60/0.20 임계값과 순위 가중치는 경험적으로 조정할 초기값이다. 실제 자연스러움과 적절성은 별도 사용자 평가가 필요하다.

## 2026-11-06 후속 변경: 대화 자유도와 응답 지연

이 게임의 재미는 대화이며, 응답 품질을 속도보다 우선한다. 직전 미커밋 수정의 로컬 모델 문장 선택기 제한을 제거했다. API와 로컬 모델 모두 배경·말투·관심사와 앞서 한 말을 바탕으로 새 문장을 생성한다. 답변 후보와의 일치, 특정 사투리 어미, 문장 종결 부호를 자유 생성의 통과 조건으로 사용하지 않는다. 주문·제공·평가의 실제 상태를 지어내지 않는 계약은 유지한다. 모델의 문법·사실 일관성·재미가 이 변경만으로 보장되지는 않는다.

현재는 인물별 파인튜닝이나 모델/LoRA 교체가 없다. 하나의 Qwen3-VL-8B GGUF를 CPU 서버에 유지하며, 손님 자료를 요청마다 프롬프트로 전달한다. 손님이 바뀌어도 실행 중인 모델 프로세스를 다시 시작하지 않는다. 따라서 사용자 관찰의 느림을 페르소나 튜닝시간으로 단정하지 않는다.

이번에 적용한 입력 비용 절감:

- `PersonaWrapper`: 배경·말투·소통·지식·취향·다른 면모·관심사·표현 예시를 변환층에서 준비한다. 외형 파츠·메뉴 ID 배열 등 대화에 불필요한 전체 인물 JSON을 보내지 않는다. 원본 인물 자료를 키로 최대 32개를 메모리에서 재사용하고, 자료가 바뀌면 새 래퍼를 만든다. 출력 뒤에 일괄적으로 사투리 어미를 붙이는 방식은 사용하지 않는다.
- 대화 DB를 인물별로 미리 인덱싱한다. 예시는 실제 입력/이어가는 말과 관련 있고 최근 답변을 반복하지 않는 것만 전달한다. API는 최대 3개, 로컬은 최대 2개이며 필수 답변 목록이 아니다.
- 공통 시스템 지침 → 인물 래퍼 → 실제 상황/주문/제공 → 최근 대화 → 관련 표현/마지막 입력 순으로 구성한다. 변화가 적은 정보를 앞에 놓고 로컬 요청에 `cache_prompt=true`를 명시한다. 이는 이미 기본 활성화된 llama.cpp 캐시를 사용할 수 있는 입력 배치 개선이며 새 캐시 기능을 발명하거나 답변 완성본을 재사용하는 변경이 아니다.
- `LastLocalTimings`는 `cache_n`, `prompt_n`, `prompt_ms`, `predicted_n`, `predicted_ms` 수치만 보관한다. 공통 입력 재사용은 입력 처리 비용에 도움을 주지만, 다음 토큰을 생성하는 계산 자체를 없애지는 않는다. 실제 이득은 첫 요청/같은 손님의 후속 요청/손님 교체를 구분해 측정해야 한다. [고정 엔진 버전의 KV 캐시 및 타이밍 문서](https://github.com/ggml-org/llama.cpp/blob/b12125/tools/server/README.md)를 참고했다.

응답 선택 파이프라인:

```text
입력 + 현재 방문의 문맥
  → 설정된 API
      연결/HTTP/시간초과/잘림/빈 응답/JSON 또는 오류 대사 검사 실패 → 결과 폐기
  → 같은 문맥의 로컬 자유 생성
      연결/HTTP/시간초과/잘림/빈 응답/JSON 또는 오류 대사/최근 답변 반복 검사 실패 → 결과 폐기
  → 현재 손님·상태의 적절한 DB 답변
      기준 미충족 → 인사·맞장구·되묻기 어휘의 자동 답변
  → 유효한 최종 손님 대사 한 번만 표시

취소/손님 전환/서빙/초기화 → 전체 경로 중단, 늦은 결과 폐기
```

API는 `apiTimeoutSeconds` 기본 20초, 로컬 생성은 기존 `requestTimeoutSeconds`를 사용한다. 통합 씬 `test-loop-merge02`의 기존 로컬 제한은 45초다. 연결 실패 경로만 15초간 건너뛰며 이후 다시 시도한다. 잘못된 대사 한 번으로 이후 모델 호출을 건너뛰지는 않는다. 이 휴지기는 서버 재부팅이나 연결 오류를 매 대화마다 연속으로 기다리는 것을 줄이기 위한 것이다. 첫 로컬 부팅·실제 생성 지연이 해결됐다는 의미는 아니다. 재시작은 휴지기를 초기화한다.

HTTP 오류 원문·인증 안내·스택·연결 진단은 손님 대사로 넣지 않는다. HTTP 200 안의 `speech`가 시스템 진단 형태인 경우도 다음 단계로 넘긴다. 반면 손님이 직장에서 API 오류를 고쳤다는 사연은 단어만으로 차단하지 않는다. 이는 진단 형태를 확인하는 휴리스틱으로, 모든 자연어 오류 표현을 완벽히 구분하는 의미 모델은 아니다. 마지막 자동 답변은 새 메뉴 단답 → 명확한 작별 → 적절한 DB 답변 → 어휘 조합 순서다.

### 긴 손님 대화와 사연에 대한 제안 — 미구현

첨부 주제의 공감·다른 시선·세대/지역 간 이해를 대화의 내용으로 드러낸다. 인물의 지역·나이·장애 자체를 갈등의 원인이나 정답으로 만들지 않고, 그 손님의 구체적인 바람과 상반된 마음을 중심으로 쓴다. 같은 손님과 오래 대화하면 반복 입력의 공통 부분을 재사용할 기회가 늘지만, 생성 자체의 지연을 대신 해결하지는 않는다.

추천 흐름은 **작은 단서 → 플레이어의 자유로운 질문 → 사연과 다른 관점 → 플레이어 반응에 따른 새 이야기/여운**이다. 턴 수를 채워야 다음 단계로 가는 방식이나 정해진 질문만 맞히는 방식은 피한다. 손님은 다른 화제도 받아들이고, 플레이어는 더 묻거나 서빙하고 대화를 마칠 수 있다. 대화가 이어지며 새로 만든 일상 정보는 이후에도 일관되게 유지하는 장기 문맥 설계가 필요하다. 현재 최근 기록 8개만으로 장기 기억이 구현됐다고 보지 않는다.

사연 후보는 현재 설정에서 확장하는 별도 창작 제안이다:

- 다방을 기억하는 어르신: 손주와 옛 가게에 가고 싶지만 손주가 지루해할까 봐 말을 못 꺼낸다. ‘요즘 애들은 모른다’는 결론 대신 손주가 좋아하는 방식도 알고 싶어 한다. “그때 누구와 함께 가셨어요?” 같은 질문으로 관계의 다른 면이 나온다.
- 한국어를 익히는 손님: 오늘 하고 싶은 말이 있었는데 표현이 서툴러 오해가 생겼다. 도움을 원하는 부분과 스스로 말하고 싶은 부분을 함께 갖는다. 플레이어는 정정부터 하거나 먼저 사연을 들을 수 있다.
- 자격증을 준비하는 손님: 배운 맛의 기준과 가족이 좋아하는 커피가 달라 고민한다. 취향을 평가하는 대결보다 ‘누구에게 어떤 잔을 건네고 싶은가’를 얘기하며 서로 다른 기준을 이해한다.

현재 통합 씬은 주문 손님 한 명을 상대하지만 120초 이탈·시간 감점·서빙 후 대화 종료가 있다. 긴 대화를 넣으려면 체류시간만 늘리는 대신 **음료를 받은 뒤에도 손님이 잠시 머물며 대화할 수 있는 흐름**, 대화 중 시간 감점의 의미, 플레이어가 떠나보내는 동작을 함께 정해야 한다. 타이머·별점·큐·서빙 상태와 사연 데이터는 이번에 변경하지 않았다. 긴 대화 모드, 새 사연의 실제 대사/공개 단계, 장기 기억도 구현하지 않았다.

### 이번 변경의 검증 범위

현재 소스를 Unity 6000.6.8f1의 기존 참조 목록과 Roslyn으로 컴파일했다. .NET 격리 하네스는 실제 C# 소스·JSON을 사용하되 Unity의 Resources/JSON/시간/통신을 대체했다. 16명별 자동 답변, 자유 문장 허용, 화제 전환 유지, 명확한 작별, 시스템 진단 필터, 인물 래퍼 재사용/자료 변경, 방문 문맥 분리를 확인했다. API HTTP 오류 7종 및 비정상 응답 7종의 로컬 전환, 양쪽 실패 후 자동 답변, 휴지기/복구, 인증 분리, 타이밍 추출, 생성 중/부팅 대기 중 취소 검사도 통과했다.

연결된 Editor가 없어 Editor 임포트/Play 검사는 하지 않았다. 빌드 생성·외부 API 호출·실제 로컬 추론·실제 입력/화면·연속 대화 품질·현재 코드의 속도 비교는 실행하지 않았다. 앞 절의 Play/55.40초 결과는 이전 코드의 기록이며 이번 변경의 실행 근거가 아니다. `CafeChatSmoke`의 검증 기대도 화제 전환 유지/명확한 작별로 갱신했지만 실행하지 않았다. [이번 검사 근거](cafe-dialogue-freedom-verification.json)를 참고한다.

## 2026-11-06 대화 UI 후속 반영

E는 현재 손님 대화, F2는 주문·이전 대화·정산 정보를 묶은 현황이다. 같은 손님의 방문 기록을 묶어 스크롤로 읽고, 현황에서 연 대화 기록은 현재 손님이어도 읽기 전용이다. E로 연 현재 대화에서만 입력할 수 있다. 상세에서 Esc는 상위 목록으로, 현황 첫 화면에서 Esc는 게임으로 나간다. E로 바로 연 대화는 Esc로 닫는다. 기록 열람은 주문/서빙 대상을 바꾸지 않는다. 대화 중에도 Tab으로 레시피를 열고 닫으며, 레시피가 열린 동안 입력을 막고 초안은 보존한다. 상단 음료 안내에는 선택한 레시피를 쓰고 숨겨진 주문 정답은 공개하지 않는다.

대화·입력 패널을 오른쪽으로 소폭 옮기고 입력 안쪽 여백과 화면/패널 좌표 변환을 보완했다. 실제 Game 화면에서 양쪽 프레임 전체와 첫 글자 표시를 확인했다. 손님 출력에는 새로 합성한 짧은 음절 효과음을 연결했으며 전체 볼륨/음소거/일시정지를 따른다. 사용자 API 정상 확인 후 추가 API 호출은 하지 않았다. 상세 실행 근거는 [cafe-ui-integration-verification.json](cafe-ui-integration-verification.json)에 기록했다.

## 현황 통합과 별도 검증 씬

F2 현황에서 주문·대화 기록·영업 정산을 선택해 확인한다. 주문 선택은 서빙 대상을 바꾸지 않으며 진행 중 주문에는 손님의 실제 요청만 보여 주고 숨긴 메뉴 정답은 드러내지 않는다. 이전 대화에는 입력창을 표시하지 않는다. E는 현재 대화와 프롬프트 전용이다. 정산 영수증과 18:00 노을은 [별도 검증 씬 및 실행 기록](cafe-status-partial-tests.md)을 참고한다.
