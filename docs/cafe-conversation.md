# 한글 잡담과 로컬 모델

`CafeSession`이 선택한 대기 손님의 첫 잡담을 표시한다. 플레이어는 커서 모드에서 왼쪽 한글 입력창에 최대 300자를 넣고 Enter/보내기로 답한다. 조합 중 Enter는 전송하지 않으며 입력 중 이동·시점 전환 키를 막는다. 전송 중에도 큐는 계속 진행한다. 손님 전환·서빙·시간 초과·중단·초기화 시 이전 요청을 폐기한다. 대화 오류는 주문과 서빙을 중단시키지 않는다.

입력창은 새 Input System과 호환되는 UI Toolkit TextField이고 나머지 HUD는 기존 IMGUI다. `CafeChatPanelSettings`·`CafeChatTheme`와 기존 NotoSansKR 폰트에서 만든 `CafeChatKoreanFont`를 Resources에서 읽는다. Input Handling 설정 변경이나 Editor 재시작을 요구하지 않는다. 입력창은 HUD와 동일한 화면 비율에 배치하며 조합 확정 프레임의 Enter는 전송에 쓰지 않는다. `tools/cafe-chat-input-check.cs`로 패널·테마·한글 글리프·문자 보존을 검사한다. 실제 OS 자모 조합은 사용자 Play 검증 항목이다.

## 검색 및 응답 정책

`Resources/CafeKnowledge/conversation.json`은 기존 96개 대기 잡담 바인딩, 첫 잡담에 연결한 32개 후속 답변, 16개 인사를 담는다. 기존 어휘와 시간·상태 조건, 손님 ID, 첫 잡담 어휘 ID, 예상 질문, 주제 단어, 말투를 연결한다. 12개 동의어 묶음과 16개 말투별 종료 문장도 포함한다. 후속 답변과 동의어는 원본 엑셀 내용과 구분한 수작업 파생 데이터다. 생성된 사용자 대화를 자동으로 DB에 저장하지 않는다.

- Unicode 정규화 후 한글을 포함한 2글자 묶음 Dice 유사도 80%와 질문 단어 포함률 20%를 계산한다. 동의어 확장을 함께 비교한다. 이는 임베딩에 기반한 의미 이해가 아닌 로컬 어휘 휴리스틱이다.
- 검색은 같은 손님과 현재 시간·상태 조건으로 좁힌다. 후보 순위는 질문/어휘 유사도 65%와 직전 자발적 잡담 유사도 35%다. 상위 세 문장의 말투와 내용을 모델 참고 자료로 전달한다. 자동 잡담의 사용 어휘 기록은 소비하지 않는다.
- 답변 생성은 설정된 API → 로컬 LLM → 자동 답변 순서다. DB 직접 응답과 문맥 캐시는 모델 호출보다 앞서 반환하지 않는다. API 설정·키 누락, HTTP 오류·시간 초과, 빈 응답·잘린 응답·대화 JSON 계약 위반 시 다음 단계로 넘어간다. 로컬 LLM은 기존 페이로드를 필요할 때 부팅하며 별도 API 키와 로컬 인증 토큰을 분리한다.
- 자동 답변은 같은 손님·현재 시간·상태 조건으로 `conversation.json`을 검색한다. 최고 유사도 후보의 점수가 `CafeSession.automaticReplyThreshold` 이상이면 그 매크로를 사용한다. 기본 기준은 0.60이며 Inspector에서 조정한다. 미만이거나 후보가 없으면 `replyVocabulary`의 손님별 맞장구·되묻기·주제 질문 어휘를 조합한다. 확실하지 않은 사실을 만들어 내지 않고 설명을 요청하며, 자발적 잡담의 사용 기록을 소비하지 않는다.
- 화제 점수는 직전 잡담, 최근 NPC 답변 두 개, 손님 소재와 동의어를 사용한다. 짧은 인사·맞장구·후속 질문은 별도로 허용한다. 낮은 어휘 점수만으로는 종료하지 않는다. 점수 0.06 미만이면서 양자역학·주식 시세·로켓 설계 등 명확한 별도 요청 패턴에 해당할 때만 자동 답변 단계에서 매크로로 닫는다. 나머지 불확실한 입력은 모델이 현재 대화와 함께 의미를 판단하며, 관련성이 불확실하면 되묻고 대화를 유지한다. 모델의 `endConversation=true`는 말투별 매크로 종료로 처리한다. 기존 speech-only 응답은 대화를 유지한다. `다시 이야기하기`로 재개한다. 유사도나 내부 ID는 게임 화면에 노출하지 않는다.
- 나머지 요청은 준비된 Qwen GGUF/llama.cpp CPU 모델로 생성한다. JSON `speech`와 한국어·길이를 검사하고 기존 메뉴명 마스킹을 적용한다. 빈 응답/잘린 응답/HTTP 오류에는 재시도 가능한 안내를 표시한다. 대화가 주문·서빙·별점 상태를 수정하지 않는다.
- 최근 기록 8개를 문맥으로 전달하며 완전히 동일한 프롬프트의 응답은 최대 64개 메모리 캐시에서 재사용한다. 다른 기록·상태의 같은 질문에는 그대로 재사용하지 않는다. 초기화하면 캐시와 대화 종료 상태도 지운다.

## 모델 및 빌드 검증 방법

### API 연결 옵션

`LocalCafeModel` 새 컴포넌트의 `backend`는 기본 `Gemini`다. 기존 씬의 직렬화된 제공자 선택은 유지한다. `CompatibleApi`로 바꾸면 실시간 생성에만 외부 OpenAI 호환 Chat Completions API를 사용한다. `apiEndpoint`에는 전체 `/v1/chat/completions` 주소, `apiModel`에는 제공자 모델 ID, `apiKeyEnvironmentVariable`에는 키 **값이 아닌 환경변수 이름**을 넣는다. 기본 이름은 `CAFE_CHAT_API_KEY`다. 키가 없는 자체 서버라면 Inspector에서 환경변수 이름을 비운다. 주소와 모델명만 직렬화되며 키는 프로세스 환경에서 읽고 디스크에 저장하지 않는다.

빌드에서도 실행 인수로 선택할 수 있다. 환경변수는 실행 전에 사용자가 설정한다. Unity Editor 역시 해당 환경변수를 상속받은 상태로 실행해야 한다.

```powershell
.\CafeChat.exe --cafe-chat-provider api --cafe-chat-endpoint https://provider.example/v1/chat/completions --cafe-chat-model MODEL_ID
```

`--cafe-chat-key-env 다른_환경변수명`으로 키의 환경변수 이름을 변경하고, `--cafe-chat-provider local`로 로컬 모델을 선택한다. API를 선택하면 실패 시 같은 요청을 로컬 LLM으로 넘긴다. `local` 명시 선택은 API 설정이 없는 오프라인 모드이며 로컬 LLM → 자동 답변 순서로 동작한다. API 준비 상태는 설정 검사 결과이며 인증·연결 성공은 첫 전송에서 확인된다. HTTPS를 요구하며 인증정보가 포함된 URL·쿼리·fragment는 거부한다. HTTP는 loopback 개발 서버만 허용한다. 호환 API가 `messages`, `max_tokens`, `temperature`, `response_format: json_object`와 `choices[].message.content` 형식을 지원해야 한다. 다른 네이티브 API 규격은 별도 어댑터가 필요하다.

실제 외부 API 호출과 키 생성은 수행하지 않는다. `tools/cafe-api-mock.py`는 루프백에서 모델명·Authorization·한글·문맥 전달·JSON 계약을 검사하며 실제 인증정보를 사용하거나 로그에 남기지 않는다.

`LocalCafeModel.PayloadPath`는 Editor에서는 `LocalInference`, Windows Player에서는 실행 파일의 `_Data/StreamingAssets/CafeLocal`이다. 씬 시작 시 자체 프로세스를 부팅하고 준비 상태를 표시한다. 준비 중에도 입력을 접수하고 준비 완료 후 순차 생성한다. 로컬 모델도 사용할 수 없으면 자동 답변으로 이어간다. `모델 재시작`은 큐를 초기화하지 않는다. 기존 검증된 페이로드를 재사용하며 패키지나 모델을 새로 설치하지 않는다.

`tools/cafe-conversation-check.cs`는 16명별 첫 잡담 매핑, 맞장구·후속 질문 허용, 무관한 질문 거절, 검색 부작용, 응답 검증 및 캐시 분리를 검사한다. 기존 큐 회귀 검사는 `tools/cafe-queue-check.cs`다.

Development 빌드에서 `CafeChat.exe --cafe-chat-smoke <절대 경로.json>`을 명시할 때만 통합 검증이 실행된다. 일반 실행이나 씬에는 자동 검사 오브젝트를 붙이지 않는다. 빌드에 포함된 모델 부팅, DB 답변, 실시간 생성 2회, 문맥 캐시 분리, 취소, 손님 전환, 화제 이탈 종료와 서빙을 검사하고 JSON과 화면 캡처를 남긴 뒤 종료한다. 합성 검사 문장 외의 사용자 대화는 저장하지 않는다. 이 검사는 API를 통한 한글 전송을 확인하며 OS IME의 실제 자모 조합 입력을 대신하지 않는다.

이전 버전의 Windows 빌드 `Builds/CafeChat-20261105-Api/CafeChat.exe`에서 로컬 모델 부팅, DB 답변, 생성·문맥 응답, 취소·손님 분리·화제 이탈 종료·서빙 검사가 모두 통과했다. CPU 생성은 27.92초와 27.06초였으며 DB 답변은 같은 프레임에 처리됐다. 같은 최종 빌드의 API 옵션도 루프백 모의 서버에서 통과했고 모델명·Authorization·한글·최근 답변 문맥 전달을 확인했다. 모의 서버 지연은 실제 외부 API 속도의 근거가 아니다.

빌드는 오류 0건으로 성공했다. 설치된 추론 패키지 compute shader의 variant 경고 496건은 남아 있다. OS IME 자모 조합 입력, 외부 API 실호출, 다른 PC 실행은 미검증이다. 실제 화면에서는 로컬 모델 준비와 대화 종료·재개 UI를 관찰했지만 사용자 입력이 감지되어 창의 키 입력 자동화는 중단했다. [현재 빌드·실행 근거](cafe-chat-verification.json)에 검사 결과를 기록했다. 빌드 자동 변경 설정과 임시 씬은 정리하고 기존 패키지는 유지했다.

## 새로운 메뉴 단답과 현재 검증

`Resources/CafeKnowledge/NewMenuRequests.json`은 표시명 **새로운 메뉴**인 별도 테이블이다. 기존 메뉴 밖 요청 4종 × 손님 16명의 64개 단답을 보관한다. 요청 ID·손님 ID로 원하는 메뉴명과 기존 주문 어미를 결합한 답변을 찾는다. 예: “카페모카 부탁하겠네.” 메뉴 밖 주문이 active 상태일 때 입력창에서 “무슨 메뉴를 원하세요?”, “그 음료는 없어요”, “대신 라떼는 어떠세요?”라고 응대하면 이 테이블의 API와 로컬 LLM이 모두 실패한 자동 답변 단계에서 원하는 메뉴 단답을 반환한다. 이 단답에는 메뉴명을 마스킹하지 않는다. 주문·별점 상태를 바꾸거나 대체 메뉴에 동의했다고 해석하지 않는다. 잡담이 종료된 뒤에도 메뉴 문의는 가능하다.

이번 버전은 빌드/Play 없이 Editor 컴파일과 접수·단답·자연스러운 후속 질문·큐·후기·데이터 검사를 통과했다. 의미 판단을 위한 새 모델 응답 계약은 코드/파서 호환성만 검사했고 실제 모델의 새 응답 품질은 미검증이다. 이전 빌드의 실행 기록은 현재 버전 성공 근거가 아니다. 사용자가 삭제를 요청한 두 CafeChat 빌드 폴더는 삭제했으며 기존 Builds/Windows와 원본 LocalInference는 보존했다.

## 입력창 표시와 다음 손님 복구

첫 손님을 일찍 서빙하면 다음 정기 입장까지 빈 화면이 생기던 문제를 수정했다. 마지막 손님의 후기 읽기 시간이 끝났고 Active/Inactive가 모두 비었을 때만 FillVacancy로 다음 손님을 입장·접수한다. 정기 입장 시각도 재설정해 중복 입장을 막는다. 다른 대기자가 있으면 기존 FIFO를 유지한다. tools/cafe-continuity-check.cs는 세션의 후기 보존 → 두 번째 손님 선택 → CanChat까지 검사하며 시간 초과와 중복 방지도 포함한다.

입력 불가처럼 보이던 원인은 두 가지가 겹쳤다. 작은 Game View에서 기본 테마의 입력칸 상하 여백 각 10px 때문에 내부 TextElement 높이가 0이 됐고, IMGUI 배경이 UI Toolkit 입력창 위에 그려져 문자와 커서를 덮었다. 입력 필드 내부 여백·최소 높이를 화면 배율과 함께 설정하고 IMGUI 배경에는 입력칸 영역을 비워 둔다. 테마의 커서·선택 색도 명시한다. 입력 활성 여부는 Repaint 대신 Update에서 갱신한다.

사용자가 이번 입력 문제에 한해 허용한 Editor Play에서 마우스 클릭 후 커서 표시, hello 한글 및 안녕하세요의 실제 입력·화면 표시를 확인했다. 수정 전 내부 문자 버퍼는 8자였지만 글자 영역 높이는 0이었고, 수정 후 같은 작은 화면에서 높이 15px를 확보했다. OS 한글 자모 조합 자체와 Enter 전송은 이번 재현 검사로 확정하지 않았다. Play는 종료했고 빌드는 생성하지 않았다.

## 2026-11-06 답변 우선순위 변경

일반 대화·새로운 메뉴 문의·화제 이탈 모두 API → 로컬 LLM → 자동 답변 경로로 처리한다. 생성 성공 시 실제 사용한 소스를 기록하며, 자동 답변의 내부 점수·ID는 UI에 표시하지 않는다. 요청 중단·손님 전환·서빙·초기화는 전체 순차 요청을 취소한다. 기존 `CafeChatSmoke`의 DB 검사는 자동 답변 함수를 직접 검사하도록 바꾸었으며 일반 실행에는 검사를 연결하지 않는다.

검증: Unity의 기존 Editor용 응답 파일과 Roslyn 컴파일러로 현재 런타임 코드를 컴파일했다. Editor Play, 빌드 생성, 외부 API·로컬 모델 실호출과 실제 화면/연속 대화 품질 검증은 실행하지 않았다.

추가 검사: .NET 격리 하네스에서 현재 C# 소스와 DB를 사용해 16명별 최고 후보·임계값 경계·어휘 조합·빈 검색·조회 무변경·종료를 통과했다. Unity의 Resources/JSON/Mathf를 대체한 검사이므로 Editor 실행 근거는 아니다. 실제 `LocalCafeModel` 소스에 모의 통신을 연결한 검사에서 API 성공 시 로컬 미호출, HTTP 오류와 잘못된 JSON의 로컬 전환, 두 모델 실패 콜백, 인증 토큰 분리를 통과했다. 실제 네트워크·추론 프로세스·취소 UX는 이 검사로 입증하지 않는다. 패키지 manifest/lock 해시는 변경 전과 동일하다.

## 어휘 조합의 후보 생성·필터·순위 선택

`CafeReplyComposer`가 낮은 유사도 자동 응답의 최종 문장을 선택한다. 입력의 대화 행위를 인사·맞장구·질문·불명확 입력으로 나누고, 손님별 작성된 어휘와 현재 입력에서 근거가 확인되는 DB 주제로 후보를 생성한다. 미완성 슬롯, 중복 문장, 비정상 구두점, 길이·표현 제한을 위반한 후보는 제거한다. 관련성·대화 행위 일치도·간결성으로 점수를 매기고 최근 손님 답변 3개의 동일·유사 표현에 반복 감점을 적용한다. 근거가 부족하면 일반 확인 질문을 선택한다. 인사·맞장구에 불필요한 되묻기를 붙이지 않는다.

이는 문장 후보를 생성한 다음 필터와 순위 선택을 거치는 구조를 적용한 프로젝트 전용 규칙이다. 참고: [Generate, Filter, and Rank](https://arxiv.org/abs/1904.03279), [Joint Generator-Ranker Learning](https://aclanthology.org/2023.findings-acl.486/). 해당 논문의 학습 모델·평가 결과를 이 구현에 적용한 것으로 해석하지 않는다. 현재 필터는 한국어 문법·의미 함의를 학습한 판별기가 아니며, 0.60/0.20 임계값과 순위 가중치는 경험적으로 조정할 초기값이다. 실제 자연스러움과 적절성은 별도 사용자 평가가 필요하다.

## 2026-11-06 Unity CLI Play 확인

사용자가 이번 변경의 Play 검증을 명시적으로 허용했다. Unity CLI로 Editor 6000.6.8f1을 열고 `test-loop-merge02`에서 Play를 실행했다. 새 로직 반영 후 Unity 컴파일과 16명 전체 후보 생성·형식 필터·인사·맞장구·주제 근거·반복 감점 검사가 통과했다. 긴 입력 안의 정확한 DB 주제명이 전체 문자열 유사도 때문에 누락되던 문제를 발견해 정확한 주제 언급을 우선 인식하도록 수정했다.

- 실제 UI Toolkit TextField의 한글 문자열 설정 → Return KeyDown 이벤트 → 요청 → 모의 API 응답 → 대화 패널·말풍선 표시를 확인했다. 실제 키보드/OS IME 조합 검사는 아니다.
- 루프백 모의 API의 최종 응답은 약 0.014초였다. 한국어·모델·인증 헤더·최근 대화 전달을 확인했다. 실제 외부 API의 성공/속도 근거는 아니다.
- API 주소를 실패하는 루프백 주소로 설정한 뒤 실제 llama-server/모델 응답까지 도달했다. 최종 실행의 부팅·API 실패를 포함한 전체 지연은 55.40초였다. 이 응답에는 어색한 표현이 관찰되어 로컬 생성 품질을 충분하다고 판정하지 않았다.
- 양쪽 연결 실패 조건에서 매크로 응답 약 4.11초, 낮은 유사도의 인사 어휘 선택 약 4.09초를 확인했다. 분기 확인에 한해 임계값 0/1을 런타임에 사용했다. 저장된 기본값은 0.60이다.
- 요청 중단·손님 전환·서빙이 진행 중 요청을 취소했으며, 지연 확인 후 이전 손님의 답변 수가 증가하지 않았다.
- 최종 콘솔 오류 0, 컴파일 실패 없음, Play 종료 확인. 씬은 저장하지 않았고 패키지 manifest/lock 해시는 변경 전과 같다. 빌드를 생성하지 않았다.

구조화한 근거는 [cafe-response-routing-verification.json](cafe-response-routing-verification.json)에 있다. 자연스러움·의미 적절성의 포괄적 검증이나 한국어 평가 데이터셋 기반 성능 측정은 수행하지 않았다.
